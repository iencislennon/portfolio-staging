## Context

The Decentrathon 6.0 "Soup Kernel Challenge" fixes the training task: Soup 0.77.0, NF4 weights, LoRA rank 16, 256 Kazakh instruction examples, batch size 4, maximum length 512, one epoch of 64 steps. Solutions may add Triton kernels and other speedups but must keep the task's outputs and pass ten automatic checks, including a minimum share of runtime spent in the team's own kernels.

## My contribution

I authored 24 of the 53 commits in this repository (the rest are from two other authors). My commits cover the measurement and robustness tooling, the final-candidate measurement records, the Kaggle submission notebook and its recorded run, and the submission documentation. Which kernels I wrote is not recorded in the commit history, so I am not claiming individual kernels here.

## Constraints

One Tesla T4 (16 GB), a fixed task configuration, a fixed submission deadline, and a rule that own kernels must account for at least 5% of runtime. An earlier version failed that check at 0.46%.

The training path removes padding tokens, runs hot operations in Triton kernels and stores smaller activations for the backward pass. A separate harness measures it against unmodified Soup.

## Decisions

- **Measure paired, not once.** Each comparison runs base → solution → solution → base so drift in the shared T4 does not favour either side. Wall time is the median per side; memory is the maximum peak per side.
- **Report the weaker earlier runs too.** The README keeps two earlier comparisons (1.3366× and 1.3193× speedup) next to the final one (1.3954×) instead of showing only the best.
- **Keep failures in the evidence.** The notebook log with the five failing tests is tracked alongside the passing checks.

## Evaluation

Final submission-source run (F), public rows, seed 1: whole command 83.25 s (base) vs 59.66 s (solution); peak GPU memory 14,345 MiB vs 4,421 MiB; held-out loss 2.04966 vs 2.04942; own-kernel share 10.0% in the lowest repeat against a required 5%. All automatic checks 1–10 passed at the submitted commit.

A separate robustness run on other dataset rows (seed 7) gave 1.3193× speedup, a 3.2579× memory ratio and +0.017% held-out loss. That run is a local experiment, not the organizers' hidden evaluation.

## What failed

The first complete version failed check 4: own kernels were 0.46% of runtime against the 5% requirement, even though speed and memory had improved. Closing that gap meant moving real work into Triton kernels rather than relabelling it. The full solution test suite also still has five failures from a PEFT/torchao incompatibility in the test environment.

## Impact

Only what the measurements support: on the stated task and hardware, the submitted solution trained 1.40× faster, used 3.24× less peak GPU memory and kept held-out loss within 0.012% of the baseline. I make no claim beyond that task and a single T4.

## Next iteration

Per-module on/off experiments, an attention profile before changing its fallbacks, and fixed-policy MLP recomputation comparisons. The expected gains are unknown until those runs exist.

## Reproducibility

The repository includes a CPU-only check (`bash tools/check_local.sh`, which passes) and a Kaggle notebook configured with the submission commit and `--repeats 2`. Public visibility of that notebook has not been verified. Raw JSON for the two earlier comparison runs is not tracked in Git.
